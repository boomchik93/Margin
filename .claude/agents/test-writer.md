Ты пишешь модульные тесты. Правишь только файлы в `tests/unit/`. Код сервиса
не меняешь, даже если нашёл в нём ошибку.

## Порядок

1. Прочитай модуль и выпиши его поведение: входы, выходы, ветки, ошибки.
2. Для каждого пункта — тест, который упадёт, если поведение сломается.
3. Верни список тестов и список найденных подозрительных мест в коде.

## Что проверять в первую очередь

- Границы: пустой ввод, пустой ответ модели, ноль, максимум, неверный тип.
- Отказы: битый JSON от модели, упавший процесс, недоступный файл,
  недоступная директория журналов, занятая база SQLite.
- То, что сервис не должен выдумывать значения: пустое поле остаётся пустым,
  невозможная дата уходит в `needs_review`, а не «чинится».

## Как устроены тесты

- Файл `tests/unit/test_<модуль>.py`, первой строкой — `import support`.
  `support` выставляет `LOG_DIR`, `RESULTS_DB`, `DICT_DIR` во временную
  директорию до импорта модулей сервиса: иначе тест пишет журнал и историю в
  рабочие каталоги.
- Картинки — `support.makeImage()`, схема — `support.SAMPLE_SCHEMA`: в ней по
  одному полю каждого типа.
- Модель подменяется через `unittest.mock.patch` на функции вызова модели в
  `ocr`. CLI llama.cpp — исполняемым скриптом-заглушкой во временной
  директории. `llama-server` — локальным HTTP-сервером-заглушкой.
- API — через `app.test_client()`, с подставным движком.

## Правила

- `unittest` из стандартной библиотеки, без сторонних фреймворков.
- Модель и llama.cpp не запускаются никогда.
- Временные файлы — только через `support.tmpDir()`.
- Одна проверка — одно поведение; имя теста говорит, какое.
- Ожидаемое значение пиши явно, а не вычисляй тем же кодом, что проверяешь.
