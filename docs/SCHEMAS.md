# Схемы полей и словари

Схема описывает документ: какие поля на нём есть, какого они типа и как их
проверять. Из схемы сервис сам собирает промпты модели, пустой результат и
правила нормализации, поэтому новый вид документа добавляется без правки
кода.

## Где лежат схемы

`config/schemas/*.json`. Имя файла без расширения — имя схемы:
`config/schemas/invoice.json` вызывается как `schema=invoice`. В имени —
латиница, цифры, дефис и подчёркивание.

Новый или изменённый файл подхватывается на следующем запросе, перезапуск не
нужен. Файл с ошибкой не загружается целиком — причина видна в
`GET /api/schemas` в поле `errors` и в журнале.

Схему можно и не класть на сервер, а передать в запросе полем `schema_json`.

## Минимальная схема

```json
{
  "fields": [
    {"key": "recipient", "label": "Кому"},
    {"key": "date", "label": "Дата", "type": "date"}
  ]
}
```

## Полный формат

```json
{
  "title": "Заявка на пропуск",
  "description": "Бланк с печатными подписями полей и рукописными ответами",
  "language": "ru",
  "fields": [ ... ],
  "zones": [ ... ]
}
```

| Ключ | Описание |
|---|---|
| `title` | Название документа. Попадает в промпт и в веб-интерфейс |
| `description` | Одна фраза о документе; попадает в промпт |
| `language` | Язык рукописи: `ru` (по умолчанию), `en`, `auto` или название языка |
| `fields` | Поля, от 1 до 100 |
| `zones` | Зоны повторного чтения, необязательно |

### Поле

```json
{
  "key": "city",
  "label": "Город",
  "type": "text",
  "hint": "Одно слово",
  "required": true
}
```

| Ключ | Описание |
|---|---|
| `key` | Ключ в ответе. Латиница в нижнем регистре, цифры, подчёркивание; начинается с буквы. Обязателен |
| `label` | Как поле подписано на документе. По нему модель находит поле, поэтому пишите подпись так, как она напечатана |
| `type` | `text` (по умолчанию), `number`, `date`, `phone`, `checkbox` |
| `hint` | Подсказка модели про это поле. Необязательно |
| `required` | `true` — пустое поле попадёт в `needs_review` |

### Типы

**`text`** — строка. Пробелы схлопываются.

| Ключ | Описание |
|---|---|
| `case` | `upper`, `lower` или `keep` (по умолчанию) |
| `format` | Регулярное выражение, которому значение должно отвечать целиком. Несовпадение — `format_bad` и ручная проверка |
| `dictionary` | Имя словаря допустимых значений, см. ниже |
| `max_dist` | Порог исправления по словарю для этого поля |

Без `format` проверить свободный текст нечем (`unverified`, оценка 55);
браком считаются только явные срывы чтения — четыре одинаковых символа
подряд и слова, где смешаны латиница и кириллица.

**`number`** — число. Пробелы внутри убираются, запятая на точку не
меняется.

| Ключ | Описание |
|---|---|
| `min`, `max` | Границы допустимого значения |

**`date`** — приводится к `ДД.ММ.ГГГГ` из разделителей `.`, `/`, `-` и
пробела. Двузначный год достраивается так, чтобы дата не ушла в будущее
дальше десяти лет. Невозможная дата (`32.13.2024`) не исправляется: остаётся
как прочитана с причиной `format_bad`.

| Ключ | Описание |
|---|---|
| `min_year`, `max_year` | Границы года |

**`phone`** — остаются цифры и ведущий `+`. Ничего не дописывается.

| Ключ | Описание |
|---|---|
| `digits` | Точное число цифр. Без него допустимо от 7 до 15 |

**`checkbox`** — отметка: галочка, крестик, закрашенный квадрат, подпись.
Значение — `checked`, `unchecked` или `unclear`.

### Как писать подсказки

- Не приводите пример значения. Модель копирует образец: с подсказкой
  «например 01.02.2003» эта дата окажется в пустом поле. Описывайте формат
  словами или маской: «шесть цифр», «ДД.ММ.ГГГГ».
- Пишите про то, в чём модель ошибается на ваших документах: «год вписан
  двумя цифрами после напечатанного 20», «первая цифра уже напечатана на
  бланке — включи её».
- Короткая подсказка работает лучше длинной. Правила про различение похожих
  букв конкурируют между собой: усилив внимание к одному полю, можно
  ухудшить соседнее. Проверяйте правку на всём наборе полей, а не только на
  том, ради которого она сделана.

## Зоны

Зона — прямоугольник страницы, который отдаётся модели отдельным проходом.
На фрагменте символы крупнее и читаются точнее, чем на странице целиком.
Каждая зона — ещё один вызов модели, поэтому заводите их для полей, которые
читаются плохо.

```json
"zones": [
  {
    "name": "header",
    "box": [0.05, 0.10, 0.95, 0.35],
    "fields": ["recipient", "city"]
  },
  {
    "name": "phone",
    "box": [0.05, 0.40, 0.80, 0.46],
    "fields": ["phone"],
    "vote": true
  },
  {
    "name": "date",
    "box": [0.60, 0.92, 1.00, 1.00],
    "fields": ["date"],
    "override": true,
    "hint": "Росчерк подписи слева к дате не относится"
  }
]
```

| Ключ | Описание |
|---|---|
| `name` | Имя зоны, видно в журнале |
| `box` | `[x0, y0, x1, y1]` в долях страницы от 0 до 1: левый верхний и правый нижний угол |
| `fields` | Ключи полей, которые читаются в зоне |
| `hint` | Подсказка модели про этот фрагмент |
| `override` | См. ниже |
| `vote` | См. ниже |

**По умолчанию зона только дополняет.** Она заполняет поля, которые
полностраничный проход оставил пустыми, и не трогает уже прочитанные.

**`override: true`** — непустой ответ зоны замещает результат страницы.
Включайте там, где кроп заведомо читается лучше. Осторожно: слишком узкая
рамка срезает верх букв, модель уезжает на соседнюю строку, и `override`
даёт этому мусору право затирать верное значение.

**`vote: true`** — зона из одного поля читается три раза разными
формулировками, и итог собирается посимвольно по большинству голосов вместе
с ответом полностраничного прохода. Подходит для номеров и кодов, где ошибка
обычно в одном знаке: проходы ошибаются в разных позициях, и большинство
ошибки снимает. Итог может не совпасть ни с одним проходом целиком — сколько
проходов сошлось, видно в `trace` записи истории.

Зоны задаются в долях страницы и потому привязаны к вёрстке: они рассчитаны
на одинаково отсканированные документы одного вида. На документе другой
раскладки зонные проходы тратятся впустую. Отключить их все разом можно
настройкой `фрагментация: false`.

## Словари

Словарь — список допустимых значений поля: города, категории, коды
товаров. Лежит в `data/dictionaries/`, имя файла без расширения — имя
словаря.

```json
["Москва", "Казань", "Самара"]
```

или

```json
{
  "values": ["Москва", "Казань", "Самара"],
  "max_dist": 1.0
}
```

Поле ссылается на словарь по имени: `"dictionary": "cities"`.

### Что делает сверка

1. **Точное совпадение** без учёта регистра, `ё`/`е` и лишних пробелов —
   значение приводится к написанию из словаря (`exact`).
2. **Похожее значение** — исправляется на него (`fixed`), но только если
   задан порог `max_dist` и ближайший кандидат единственный.
3. **Остальное** остаётся как прочитано, получает статус `review` и уходит
   в `needs_review`; ближайшие значения словаря приходят в `candidates`.

### Порог `max_dist`

Это наибольшее расстояние, на котором расхождение ещё считается ошибкой
чтения, а не другим значением. Лишняя, пропущенная или заменённая буква
стоит 1.0; замена в паре похожих знаков (`Б`/`Ь`, `И`/`Н`, `4`/`9`,
латинская `P` вместо русской `Р`) стоит 0.5.

**Без порога словарь ничего не переписывает** — только подсказывает. Так
сделано намеренно: подходящий порог зависит от словаря. В списке из
пятнадцати городов расстояние 1.0 безопасно, а в списке из десяти тысяч
фамилий на таком расстоянии лежат разные люди. Подберите порог на своих
данных и только потом включайте.

Порог можно задать в файле словаря (действует на все поля, которые на него
ссылаются) или в поле схемы (важнее порога из файла).

Страховки, которые действуют всегда:

- значение короче четырёх знаков сверяется только точно;
- у значения из четырёх знаков допускается не больше одной правки;
- два кандидата на равном расстоянии — не подставляется ни один.

### Обновление

Положите новый файл в `data/dictionaries/` — он подействует на следующей
странице. Состояние — в `GET /api/dictionaries`. Битый файл пропускается с
записью в `errors`, остальные словари продолжают работать.
