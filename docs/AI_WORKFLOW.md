# Работа с агентами

Проект пишется с ИИ-агентами Claude Code. Решения, порядок работы и коммиты —
мои; агенты исполняют узкие роли и проверяют друг друга. Здесь описано, как
это устроено и почему.

## Роли

| Агент | Что делает | Чего не делает |
|---|---|---|
| `planner` | Читает код, разбивает задачу на шаги по одному коммиту, описывает контракты между модулями | Не пишет код |
| `implementer` | Выполняет один шаг плана | Не выходит за шаг, не коммитит |
| `test-writer` | Пишет модульные тесты к изменённому коду | Не правит код сервиса |
| `test-runner` | Прогоняет тесты, разбирает падения | Ничего не исправляет |
| `reviewer` | Ревью диффа: ошибки, стыки модулей, выдуманные данные, приватность | Ничего не исправляет |
| `docs-writer` | Документация по коду: API, схемы, настройки, архитектура | Не правит код |

Определения — в [`.claude/agents/`](../.claude/agents/), правила проекта для
всех агентов — в [`CLAUDE.md`](../CLAUDE.md).

## Цикл задачи

```
задача
  └─ planner ─── план ──► я подтверждаю
                            └─ для каждого шага:
                                 implementer ─► test-writer ─► test-runner
                                      ▲                            │
                                      └──── падение из-за кода ────┘
                            └─ reviewer на весь дифф
                                 └─ находки ─► implementer ─► test-runner
  └─ я читаю дифф и коммичу по шагам
```

Запускается командой `/feature <описание>`. Отдельно: `/test <модуль>` —
тесты для модуля, `/review [ветка]` — ревью, `/docs [раздел]` — документация
под текущий код.

## Почему так

- **Тесты пишет не тот, кто писал код.** `test-writer` видит модуль, но не
  видит рассуждений `implementer`, поэтому не повторяет его ошибок в
  ожиданиях.
- **Тестировщик и ревьюер ничего не исправляют.** Иначе находка тихо
  исчезает внутри правки и не доходит до меня.
- **Один шаг — один коммит.** Маленький дифф реально прочитать целиком,
  прежде чем коммитить.
- **Агенты не видят документов.** Сервис обрабатывает персональные данные,
  поэтому `uploads/`, `logs/`, `data/in`, `data/out` и `.env` закрыты в
  [`.claude/settings.json`](../.claude/settings.json). Для проверок есть
  синтетические картинки и заглушки модели.
- **Коммиты и пуш — только вручную.** Запрещено в настройках, а не
  только в тексте промптов.

## Что поменялось по ходу

- **Ревьюер получил список стыков модулей.** Первый общий проход ревью после
  API нашёл пять ошибок, и все — на границе двух модулей: пустой ответ модели
  считался пустой страницей, замена гомоглифов портила латинские коды,
  словарь предлагал далёких кандидатов, история сравнивала даты в разных
  форматах, поля в ответе шли не в порядке схемы. Каждый модуль по
  отдельности был верен. Теперь эти стыки — обязательный пункт ревью.
- **Тестировщик знает устройство тестов.** Без явного описания `support.py`
  тесты писали журнал в рабочий `logs/` и поднимали настоящий процесс
  llama.cpp. Теперь правила подмены модели и временных директорий записаны в
  определении агента, а `test-runner` считает мусор в рабочих каталогах
  находкой.
- **Документацию пишет отдельный агент по коду.** Тексты, написанные по
  памяти о том, как задумывалось, расходились с кодом в мелочах: имена
  параметров, значения по умолчанию, коды ошибок. `docs-writer` берёт
  примеры ответов из реального прогона, а `reviewer` сверяет текст с кодом.
- **Линтер — сразу после правки, а не на CI.** С появлением `ruff` в CI
  агенты стали получать замечания только после пуша. Хук `PostToolUse` в
  `.claude/settings.json` прогоняет `ruff check` по каждому изменённому
  `.py`-файлу и возвращает замечания агенту, который его правил.
