# Как устроен сервис

Документ описывает путь данных от загруженного файла до JSON, устройство
каждого этапа и причины принятых решений.

## Задача

Рукописный текст сложнее печатного по двум причинам.

1. **Нужно отделить рукописное от печатного.** На анкете подписи полей
   напечатаны, ответы вписаны от руки, и в результат должны попасть только
   ответы.
2. **Значение определяется местом.** Одно и то же число «117» — номер
   квартиры в одной строке и количество в другой.

Поэтому вместо классического OCR используется vision-language модель: она
видит страницу целиком и понимает расположение, а не только начертание букв.
Классический OCR вернул бы плоский текст без привязки к полям.

## Путь данных

```
POST /api/ocr
      │
      ├── before_request: request_id -> contextvars (сквозной по всем записям)
      ├── проверка: расширение, схема, наличие модели, лимит запросов
      ├── PDF? ──> extractImagesFromPdf() ──> PNG постранично
      ▼
Engine.readPage()                     одна страница за раз, под блокировкой
      │
      ├── без схемы ──> recognizeText()
      │       ├─ preprocessImage()    апскейл + CLAHE + шумоподавление
      │       ├─ модель: textPrompt   один проход
      │       └─ parseLines()         строки из JSON; при сбое — текст как есть
      │
      └── со схемой ──> recognizeForm()
              ├─1─ preprocessImage()
              ├─2─ модель: fullPrompt           полностраничный проход
              │       └─ extractJson() -> enforce()
              ├─3─ для каждой зоны схемы:
              │       cropRegion() -> модель: zonePrompts -> _mergeZone()
              ├─4─ charVote()                   сведение голосов зон с vote
              ▼
          postprocessForm()
              ├─ normalizeResult()              формат по типу поля
              ├─ applyDictionaries()            сверка со словарями
              ├─ scoreResult()                  уверенность по формату
              ├─ reviewQueue()                  очередь ручной проверки
              └─ трассировка стадий
      ▼
recordPage()
      ├── logging_setup.audit()       logs/audit.jsonl
      └── storage.save()              data/results.db
      ▼
JSON
```

## Этапы

### Предобработка

- **Апскейл до 2200 px** по длинной стороне, не больше чем втрое. Информации
  он не добавляет, но даёт модели больше визуальных токенов на символ.
- **CLAHE** — локальное выравнивание контраста. Вытягивает бледную пасту, не
  пересвечивая фон.
- **Шумоподавление** — убирает зерно скана, которое модель принимает за
  штрихи букв.

Если предобработка не удалась, читается исходный файл: он хуже
подготовленного, но много лучше отказа.

### Промпты

Промпты собираются из схемы (`schema.py`), а для свободного текста — в
`ocr.textPrompt()`. Правила в них появились по следам конкретных ошибок:

| Правило | Какую ошибку лечит |
|---|---|
| Только рукописное, печатные подписи игнорировать | Модель вписывает подпись поля в его значение |
| Только кириллица, со списком пар `P→Р`, `C→С`, `O→О` | В русском слове появляется латинская буква: на вид то же, а поиск и сверка слово не находят |
| Пустое поле — пустая строка | Модель «дочитывает» незаполненное поле |
| Образец ответа с пустыми значениями | Заполненный пример переписывается в пустое поле как прочитанное значение |
| Формат маской («ДД.ММ.ГГГГ»), а не примером | То же: пример даты оказывается в результате |
| Неразборчивое слово — знак `[?]` | Модель подставляет слово, подходящее по смыслу, и оно неотличимо от прочитанного |
| `unclear` как отдельное значение отметки | Без него «не разглядел» сливается с «отметки нет» |

Про пример в промпте стоит сказать отдельно. Образец вида
`{"phone": "89001234567"}` модель копирует буквально: именно это число и
возвращается для пустых и трудных полей. Поэтому образец ответа всегда
пустой.

### Зонные проходы

Зона — прямоугольник в долях страницы. Кроп вырезается из уже
подготовленного изображения и подаётся модели отдельно: на фрагменте символы
крупнее.

Слияние (`_mergeZone`) по умолчанию только **дополняет**: зона заполняет
поля, которые полностраничный проход оставил пустыми. С `override` непустой
ответ зоны **замещает** общий. У отметок «пустого» значения нет, поэтому там
правило другое: ответ зоны принимается, когда он определённее прежнего —
`unclear` уступает `checked` и `unchecked`, а уверенный ответ не затирается.

Каждая зона — дополнительный вызов модели, и это основная цена точности.

### Голосование

Для зоны с `vote` одно поле читается три раза **разными формулировками**
промпта. При температуре 0 повтор того же промпта дал бы тот же ответ;
независимые прочтения получаются только сменой формулировки.

`charVote()` сводит голоса посимвольно: среди голосов преобладающей длины в
каждой позиции берётся символ большинства. Проходы ошибаются в разных
знаках, поэтому итог может не совпасть ни с одним проходом целиком — и быть
верным. Голос основного прохода участвует наравне с зонными.

Одного голоса зоны недостаточно: он равноправен основному проходу, и выбрать
между ними не из чего. В этом случае остаётся значение основного прохода.

### Постобработка

Принцип: **приводить формат, но не выдумывать данные.** Ни одно поле не
заполняется значением по умолчанию, и ни одно значение не «чинится» до
правдоподобного. Невозможная дата остаётся как прочитана и уходит на
проверку: честнее вернуть сомнительное значение с пометкой, чем заведомо
подменённое без неё.

Порядок стадий важен:

1. **Нормализация** — регистр, пробелы, разделители дат, гомоглифы.
2. **Сверка со словарём** — по уже нормализованному значению, иначе даже
   точный кандидат не найдётся из-за лишнего пробела.
3. **Уверенность** — считается по значению **до** сверки: оценивается то,
   что прочитала модель, а не подстановка словаря. Иначе исправленные
   значения получали бы лучшую оценку из всех.

Все три состояния значения сохраняются в трассировке (`recognized`,
`normalized`, `final`), и по ней видно, чья работа привела к итогу.

### Гарантия структуры

Клиент всегда получает один и тот же набор ключей, что бы ни вернула модель:

1. `extractJson()` — устойчивый разбор: срезает служебные токены чата и
   markdown-обёртки, ищет сбалансированный `{...}` с учётом строк и
   экранирования, чинит хвостовые запятые.
2. `schema.enforce()` — добавляет отсутствующие ключи, выбрасывает
   посторонние, приводит типы.
3. `Engine.readPage()` — при любом исключении возвращает страницу с полем
   `error` и, для схемы, с полным набором пустых полей.

Молчание модели при этом не выдаётся за пустой документ: пустой ответ
помечается `error: model_no_response`, и HTTP-слой отвечает 502.
